## 0. 絶対に動かさない前提

### 拡散の設計原則

> 何かを多くの人に広め、見てもらうために最も重要なのは、**自分が必死に宣伝して広めることではなく、他人が勝手に集まり、広めたくなる「仕組みや環境」をデザインすること**である。

**この原則は再検討しない。** 以下はここから導かれる帰結であり、意見ではない。

- 宣伝文は書かない。広める側の動機は**自己表現・互恵・所属**の3つしかなく、宣伝文はそのどれも与えない（与えているのは作者の都合）
- 「使ってみて」と頼む導線を作らない。頼まれた側に**見せたくなる理由が無い**
- **作るべきは、見た人が自分の意思で他人に見せたくなる出力そのもの**

ThreeBody で唯一**文脈なしに見て分かる**出力は、**主体の答えと、それを別の知性が検算した指摘が並んでいる状態**（2026-08-20 の反転後）。統合された1つの答えは他のチャットAIのスクリーンショットと区別がつかず、共有する動機が立たない。ここが拡散の資産であり、他は全部その支援でしかない。

### 広がる単位の5条件（2026-08-20 追記）

原則を実装できる形へ落とすと、共有される対象が満たすべき条件は5つ。

1. **単体で意味が分かる** — 前後の文脈なしに見て分かる
2. **アドレスがある** — URLで指せる
3. **配るコストが増えない** — 見る人が増えても運営の負担が増えない
4. **出所が残る** — 共有先から元へ辿れる
5. **使われるほど中身が増える** — 収集のための作業がゼロ

①〜④は「よく燃える薪を配ること」、⑤は「薪が生える山を持つこと」。運営が回し続けなくても止まらないのは⑤だけ。

> **導かれる原則 — 広がる単位は、機能の副産物として自動生成する。広報のために別途作らない。**

**この原則から外れるので作らない**: 招待コード / 紹介報酬 / シェアボタンの装飾 / デモ動画の量産。いずれも運営が回し続けないと止まる。

**音声は原理的に条件1〜4を満たさない。** 声はURLにならず、検索も引用もされない。声を選んだ代償なので、拡散の単位は音声の外側（テキストとして残る検算）から出すしかない。

### 到達点（確定・再検討しない）

Application-centric → Intent-centric。意図の処理を**単一の知性ではなく複数の視点で行い、その過程が見えて聞こえる**。

### 作るときのルール

> **消費者のいない機能を作らない。** 着手前に「誰が・いつ読むか」に答えられなければ着手しない。

（`TurnSignals` はこれに違反した。3つのシグナルを貯める側だけ作り、読む側が今も存在しない）

## 1. いま効く3つ

この3つは1本の因果で繋がっている。**順序を入れ替えられない。**

```
① 声を人間らしくする   →  自分が毎日使う道具になる
② 三体の答えの質を上げる →  人に見せる価値のある出力ができる
③ 見解の共有          →  他人が勝手に広める仕組みが立つ
```

### ① 声を人間らしくする

**現状**: Web Speech API の `SpeechSynthesis`（OS標準の合成音声）。本人が「一番のボトルネック」と明言。未着手。

**やること**: AivisSpeech（VOICEVOX互換・ローカル）を音声出力の経路に足す。プローブは `aivis-probe.mjs` に用意済み、アプリ本体は未インストール。

**やらないこと**: ASR（聞く側）の差し替え。ウェイクワード専用エンジン。クラウドTTSへの課金。

**完了判定**: 自分が読み上げを切らずに1日使える。

> **併走する決定** — 全文読み上げをやめ、冒頭の要点だけを読む。長文とコードは画面に送る（カーナビ型）。読む量を減らすほど声質が体験の全部になるので、**量を絞ってから声を良くする**順序を守る。

### ② 三体の答えの質を上げる

**現状**: 副体の作り直しを実施（2026-08-20）。その後、統合そのものを廃止して検算へ反転した（下の決定）。

実測（2026-08-19、Pinterest の設計を4回聞いた）で出ていた症状と、その原因:

| 症状 | 原因 |
|---|---|
| 副体2体が**同じ内容**を書く | 視点の差が「楽観／懐疑／現実」という**態度**しかなかった。同じモデル・同じ入力・同じ出力形式なら、態度の形容詞では割れない |
| 副体が「なるほど」で始めて**普通に回答する** | 副体に会話人格（`BASE_PERSONA`）を丸ごと渡していた。そこには「相槌は『なるほど』」「相手の言葉を受ける→問い返す」が入っている。**指示どおりに動いていた** |
| 副体が**事実を作る** | 出力に不確かさの置き場が無く、断定するほど良い回答に見える形をしていた |
| **繰り返すほど答えが薄くなる** | 副体にも履歴全文（＝主体の過去の回答）を渡していた。副体はそれを読んで「すでに述べたとおり」の側へ逃げる |
| コスト +33% | 支配項は出力ではなく入力で、その入力が体の数だけ倍化していた |

**やったこと**（`backend/llm/secondaryPrompt.ts` に集約）:

1. **役ごとに答える対象を変えた。** 態度ではなく担当を割る — 二体「崩れる点」／三体「最初の一手」／（別枠）「別の見方」。出力は見出し3行の固定形式で、**中身が重なりようがない**
2. **副体から会話人格を外した。** 副体の出力はユーザー宛の発言ではなく主体だけが読む検討メモ。挨拶・相槌・問い返し・具体物・一般論を明示的に禁じ、挙げるのは1つだけに縛る
3. **「確度」を必須スロットにした。** 確認していないことは「未確認: ○○」と書かせ、統合側には「確度: 低／未確認は事実として書かない」を渡す
4. **副体への入力を直近だけに畳んだ。** 履歴全文をやめ、user 1件（＝最後の問い＋直前の応答の冒頭300字）に統一。薄まりとコストの両方がここで戻る
5. **挨拶では副体を呼ばない**（`needsMultiBody`）。形式を固定した副作用で見解の文字数では挨拶を弾けなくなったため、問いの側で先に落とす
6. **副体の指示をバックエンド1箇所へ寄せた。** フロントは `role` を送るだけ（`personaPrompt` は廃止）。自前キー経路と共有キー経路で文面がズレていた不具合の根を断つ

**完了判定**: 同じ問いに対し、副体2体が**別のことを言っている**出力が3例出る。

**→ 達成（2026-08-20）。** 壊れている側（llama3:8b、ローカル）で3問とも二体「崩れる点」と三体「最初の一手」が別の内容を返した。「なるほど」開始・普通の回答・コードの混入は0件。確度は自発的に「低／中」が付いた。

> **副作用として直したもの** — 会話人格を外した結果、言語の指示まで消えて小さいモデルが英語へ流れた（実測: llama3:8b）。副体の system に「問いと同じ言語で書く」を持たせて解消。設定の `language` ではなく問いに紐づけるのは、backend が設定を受け取らないため。

**残っていること**: 統合（主体）側の出力品質は、主体のモデルの能力そのものに戻った。小さいモデルを主体にすると依然として事実を作る（実測: llama3:8b が「サーバーアーカイブ」を発明した）。これは副体側の問題ではないので、②では追わない。

**なぜ③より先に②が要るか**: ③で共有するのは「答え＋検算の指摘」。指摘が一般論だと**共有しても面白くない**。②が終わっていない③は空箱になる。

**やらないこと**: 副体を増やす。モデルを増やす。プロンプトの微調整を繰り返す（Claude三体で正しく動く＝プロンプトは正しい。壊れているのは小さいモデル側）。

> **決定（2026-08-20）— 統合をやめ、順序を反転して「検算」にする。**
>
> ②で副体の質は直った（別々のことを言うようになった）が、**答えの質は上がらなかった**。
> 統合の有無だけを変えた対照実験（`scripts/experiment-synthesis.ts`、事実照会型と設計相談型の2問）:
>
> | 指標 | A 単体 | C 見解2件（統合） |
> |---|---|---|
> | 副体メモ由来の観点が主体へ移った数 | — | 平均 0.1/run |
> | 単体なら出ていた観点が落ちた数 | — | 平均 1.2/run |
> | 具体名の数 | 2.8 | 1.0 |
> | 留保の数（板挟みの指標） | 2.8 | 1.6 |
>
> **入ってこないのに、出るものだけが減っていた。** 板挟み仮説（副体の意見に挟まれて
> 両論併記になる）は否定された。原因は副体の中身ではなく、主体に「答える」と「まとめる」の
> 二役を負わせたこと。統合層は禁止事項の列挙（メモに言及するな・見出しを使うな・固有名を
> 写すな）で、主体の注意は問いより先に規則との照合へ向かう。具体名が 2.8 → 1.0 に落ちたのは
> 「心当たりの無い名前は捨てろ」を守った結果、元々知っていた名前まで巻き添えで落ちたため。
>
> **反転後の流れ**: 主体が単体プロンプトのまま先に答える → その答えを副体2体が読んで
> 指摘を1つずつ書く → 指摘は答えの**下**にカードで並ぶ。
> 副体の役は「答えの何を見るか」で割る — 二体「崩れる点」／三体「抜けている点」／（別枠）「別の見方」。
> 指摘が無いときは「指摘なし」と書かせる（無い指摘をひねり出させない）。
>
> **これで直るもの**: 主体は単体と同一のプロンプトで答えるので、脱落 1.2 が構造的に消える。
> 副体ラウンドが本文の前から後ろへ移るので、最初の一文が届くまでの待ち時間も縮む。
> 音声は本文だけを読み上げ、`answer_done` で読み上げを締めるのでカードの完了を待たない。
>
> **契約の変更**: SSE は `answer_start` → `text` → `answer_done`(review 有無) → `body_start`/`body_text`/`body_done`。
> `synthesis_start` は廃止。`aiState` は `idle → thinking → converging → reviewing → idle`。
> `buildSynthesisLayer` は本番経路から外したが**消していない** — `scripts/experiment-synthesis.ts` が
> 統合方式との比較に使う。別モデル・別プロバイダーで測り直す手段を失うと、この判断自体を検証できなくなる。
>
> **残る宿題（この判断が覆りうる条件）**: 上の測定は ollama の同一モデル三体でしか行っていない。
> 同じ分布のモデルが割れるのはサンプリングのゆらぎなので、「統合が無効」ではなく
> **「同質な見解の統合は無効」**までしか言えていない。異プロバイダー混成での再測が要るが、
> クラウドキーは keyVault で暗号化されていて平文で置けず、測る装置がまだ無い。
> また、指摘の有用性（検算が本当に役に立つ指摘を出すか）は自動判定できない。目視で数える。

**完了判定（検算）**: 同じ問いで、副体の指摘が**主体の答えに実際に書かれている中身を指している**出力が3例出る（一般論ではなく）。

### ③ 見解の共有

**現状**: 見解の永続化まで完了（2026-08-19）。共有URL（`/s/:token`）と公開経路を実装し、**DBを本番適用済み（2026-08-27）**。読み書き経路・UI起点・ログイン後リダイレクトまで実装完了（下記追加実装、2026-08-21）。未ログイン閲覧→新規登録→再質問のフローは自テスト2アカウントで動作確認済み。**他人（自分以外）による新規登録の実績はまだ無い**（完了判定の未達分）。**前提に直接対応する唯一の項目。**
カードの中身は 2026-08-20 の反転で「答える前の検討メモ」から「答えを読んだ上での検算」に変わった（②の決定）。共有する対象もそちらになる。

**やること**: 1ターン（主体の答え＋副体の検算カード）を、**ログイン不要の読み取り専用URL**として書き出す。保存済みの `text` と `perspective` を静的に読むだけで、生成側は触らない。

**この設計が効く理由**: 閲覧側は LLM を呼ばない。**何人見ても無料枠が1回も減らない。** 拡散とコストを切り離せる唯一の経路であり、「律速は資金」という制約を迂回する。

**やらないこと**: コメント・いいね・一覧ページ・OGP自動生成・ユーザープロフィール。

**完了判定**: 共有URLが未ログインで開き、そこ経由の新規登録が1件。

> **決定（2026-08-21）— 共有の形。**
>
> **公開の単位は1ターン**（主体の答え＋その問い＋検算カード）。問いを外すと、カードが
> 何を指しているのか読めず、5条件の1（単体で意味が分かる）が立たない。
>
> **RLS は台帳方式で開ける。** `shared_messages`（token / message_id /
> question_message_id / user_id / revoked_at）を新設し、`messages` と `content_blocks`
> に `*_select_shared`（to anon）を1本ずつ足す。条件は「台帳に生きた行があること」だけ。
> 検討した他の2案を採らなかった理由:
>   ・バックエンド経由（service_role で読む）… 閲覧のたびに自前サーバーを通る。
>     LLM は呼ばないので枠は減らないが、条件3（配るコストが増えない）を弱める
>   ・公開用テーブルへスナップショット … 正本が2つになり、会話を消しても共有が残る
>
> **URLは token で、message_id ではない。** message_id はアプリ内の他の文脈にも出る
> IDなので、それが公開URLだと「共有していないものが漏れた」と「共有したものが読まれた」を
> 区別できない。取り消しは `revoked_at` の1列で、生きている共有は1メッセージにつき1件
> （部分ユニーク）。再共有では新しい token が出る＝古いURLは復活しない。
>
> **共有ボタンは検算カードが付いたターンにだけ出す。** 統合された1つの答えは他の
> チャットAIのスクリーンショットと区別がつかない（0章）。
>
> **副体の「指摘が出たか」を構造にした**（`hasReviewFinding` → SSE `body_done` の
> `hasFinding` → `content_blocks` の payload）。本文の「指摘なし」という文字列を
> 読む側それぞれが見に行く形だと、⑤（実例の自動公開）が文面の揺れで静かに壊れる。
>
> **本番適用済み（2026-08-27）。** schema.sql 章3-9 を流し、
> `scripts/verify-share-rls.mjs` で両方向（共有したものは読める / 共有していないものは読めない）を確認済み。

> **追加実装（2026-08-21、③の続き）**
>
> - 共有ターンの読み書き経路（`useSharedTurn.ts` / `SharedTurnView.vue` / router）を実装（`7368175`）
> - 共有の起点を UI に置いた。検算カード付きのターンにだけ「この検算を共有する」ボタンを出し、質問メッセージIDも同時に持たせた（`327ff46`、`MessageBubble.vue`）
> - ログイン後のリダイレクト先を `sessionStorage` で1つだけ覚える `postLogin.ts` を追加。共有ページ経由の未ログイン閲覧者がログイン後に同じ問いへ戻れる。入力欄には前回の問いを事前入力する（`f46b767`）
> - 副体の「指摘が出たか」を構造化する `hasReviewFinding` を実装。SSE の `body_done` に `hasFinding` を載せ、`content_blocks` のペイロードまで届くようにした（`7903132`）。上のRLS決定で計画していた構造化が実装完了
> - **`hasReviewFinding` を「判定だけ」から「判定＋対象箇所の引用照合」へ強化。** `REVIEW_SLOTS` の出力を3行固定見出し（例: `崩れる点/なぜ/確度`）から4フィールド（`判定/対象箇所/根拠/代替案`）へ変え、`判定` は `指摘あり/指摘なし` の真偽、`対象箇所` は答え本文からの一字一句引用と定義した。`hasReviewFinding(content, answer)` は `判定` が「指摘あり」でも、`対象箇所` が `answer` に実在しない（正規化後の部分一致が無い、または6字未満で実質どこにでも一致する）場合は `false` へ倒す。理由: 旧実装は1行目の文字列に「指摘なし」が含まれるかしか見ておらず、対象箇所が答えに実在するかは誰も検証していなかった。②の完了判定（副体の指摘が主体の答えに実際に書かれている中身を指している）を自動では守れていなかった穴を塞いだ。`backend/llm/secondaryPrompt.ts`
> - **write済み・read未実装の穴を埋める集計スクリプト `scripts/view-shared.mjs` を追加（2026-09-01）。** `conversations.shared_from`（①の再実行計測トークン）と `content_blocks.payload.hasFinding`（②の指摘構造化）はどちらも書き込み経路だけが実装済みで、読み出し・集計が一度も無かった。同型の穴なので1本にまとめて着手。RLSがユーザー単位のため anon key では全件集計できず、`backend/supabaseAdmin.ts` と同じ service key（RLSバイパス）で読む。①は発行済み `shared_messages` トークン数を分母に、`shared_from` が実在トークンを指す会話数を分子にする（トークンに対応する行が消えないよう `revoked_at` で取り消す設計のため、取り消し済みシェアも分母に残る＝計測上の問題にはならない）。②は `content_blocks.type='perspective'` の行数を分母に、`bodies[].hasFinding===true` が1体以上のターンを分子にする。`hasFinding` を足す前の旧データは `undefined`（＝不明）であり `false`（割れなかった）と区別し、不明を除いた率も別掲する。
> - **実測値（2026-09-01、`scripts/view-shared.mjs` 実行結果）** — ①再実行率: 発行済みシェア5件中、`shared_from` が実在トークンを指す会話1件（20.0%）。この1件は開発者自身の自テストによる再実行で、③の完了判定にある「他人による新規登録」とは別物（分母も5件と小さく、傾向を読むには早い）。②割れた率: 検算対象45ターン中21ターンで副体が指摘あり（46.7%）。`hasFinding` が無い旧データ23件を除いた既知データ内では21/22＝95.5%。

> **次に立つもの（③の完了後・2026-08-20 追記）** — 5条件の⑤に当たる。副体が指摘を出したターンだけを抽出し、「AIがどこで崩れたか」の実例として日次で自動公開する。`content_blocks` に既に溜まっているため**収集の作業がゼロ**で、使われるほど増える。普通の製品は誤りを捨てるので持っていない資産。会話は私物なので既定は非公開、公開はユーザーが許可したターンだけ。**完了判定**: 30日間、人手を介さずに実例が増え続ける。

> **決定（2026-08-19）** — `perspective` は**通常の会話経路でそのまま永続化する**。共有時スナップショット案は採らない。
>
> 理由: 共有以前に「どの体が何と言ったか」がリロードで消えていた。②の完了判定（副体2体が別のことを言っている出力が3例）すら、消えるデータでは検証できない。共有はこの上に乗る2階部分であって、1階が無いまま作れない。
>
> 実装: `block_type` に `'perspective'` を追加（**本番適用済み 2026-08-19**・`schema.sql` 章3-8）。`toBlockRows` が text と並べて書き、`toContentBlock` が読み戻す。`error` は引き続き捨てる。`flattenText` は text しか見ないため、**LLMへ送る履歴のトークンは増えない**。本文と見解は別々に insert する（`insertBlockRows`）— まとめて送ると見解が弾かれたとき本文まで巻き添えで落ちるため。

## 2. 動かせない制約

**律速は資金。** 全体枠 50回/日 ÷ 個人枠 3回/日 = 17人/日でゼロ。実際は**デイリーアクティブ30〜50人**で「本日ぶんの無料枠が終了しました」が常態化する。上限は**ユーザー数ではなく運営の財布（$0.5/日）**から来ているため、ユーザーが増えても自動では動かない。

実測: 1ターン ≈ **$0.00998**（Haiku 4.5、入力5,624＋出力871トークン）。単体比 約3倍。出力ではなく**入力が3体分そのまま3倍化する**影響が支配的。

②（2026-08-20）で副体の入力を履歴全文から user 1件へ畳んだため、この3倍は下がるはず。**再実測はしていない**ので、上の数字は据え置く。

**この制約への答えは課金ではなく③。** 課金を先に置くと、払う理由が立つ前に壁を作ることになる。

**広報の宛先は BYOK / Ollama 層に固定する。** この層は増えてもコストが増えず、「複数モデルを並べて比べたい」動機を元から持つ。**完了判定**: 自分以外の BYOK / Ollama ユーザーが3人。

共有ページの導線は「登録する」ではなく「**同じ問いを自分のモデルで検算させる**」にする。条件3（配るコストが増えない）を入口そのものへ埋め込む形。

# 用語集

このプロジェクト固有の用語のみ記す。一般的なプログラミング概念は含めない。用語は確定した時点で随時追記する（現時点では以下の中核語のみ）。

**主体**:
ユーザーの問いに最初に答える体。単体モードと同一のプロンプトで答え、他の体の存在を一切知らされない。
_Avoid_: プライマリ、メイン

**副体**:
主体の答えが出た後にそれを検算する体。ユーザー宛の発言ではなく、主体だけが読む検討メモを書く。会話人格（`BASE_PERSONA`）は持たない。
_Avoid_: セカンダリ、サブ、レビュアー

**検算**:
主体が先に答え、副体がその答えを後から確認する三体モードの方式。副体の見解を主体のプロンプトへ注入して統合する旧方式（統合）とは明確に別物。
_Avoid_: 統合、レビュー

**見解 (perspective)**:
副体が検算の結果として書く指摘。`content_blocks` に `text`（本文）とは別ブロックとして永続化される。
_Avoid_: レビュー結果、コメント、フィードバック

**三体モード**:
1〜3個の体が並列に設定され、主体が先に答え副体が検算する動作モード全体。副体が全滅しても主体の答えは揺らがない。
_Avoid_: マルチエージェントモード
