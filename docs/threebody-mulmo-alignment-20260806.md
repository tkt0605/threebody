## 1. 理念と通じている点

### 1-1. 並列マルチエージェント → 統合 という GraphAI 的構造

三体モードは「依存のないノードを並列実行し、結果を後続ノードに合流させる」という
GraphAI の実行モデルそのものになっている。

| 段階 | 実装 |
|---|---|
| 並列実行 | `backend/routes/chat.ts:126` の `Promise.all` で副体（二体・三体）に同時リクエスト |
| 逐次可視化 | `backend/llm/textService.ts:25` が `body_text` を逐次 SSE 送出 |
| 合流 | `chat.ts:140` で `【○体（provider）の見解】` としてシステムプロンプトに注入 |
| 統合 | `chat.ts:157` の `synthesis_start` 後、主体が統合回答をストリーミング |

MulmoTerminal が「人間が複数エージェントを監督する」構図なのに対し、
ThreeBody は**主体 AI 自身が監督者になる**ぶん一段先に踏み込んでいる、とも言える。

### 1-2. プロバイダー中立性 / ベンダーロックイン回避

Ollama・OpenAI・Anthropic・DeepSeek を体ごとに自由に組み合わせられる設計は、
MulmoChat の provider-agnostic なテキスト生成 API、および MulmoClaude の
*"something that important should not be entrusted to any single service provider"*
と同じ思想に立っている。

### 1-3. テキストストリームからの脱却

ウェイクワード「アイリス」から音声だけで対話が完結する設計
（`useWakeWord.ts` → `useVoiceInput.ts` → `useTTS.ts`）は、MulmoChat の中心命題
*"AI conversations don't have to be limited to text streams"* と方向が一致する。
Mulmo が視覚（画像・地図・GUI）方向に拡張しているのに対し、ThreeBody は音声方向に拡張している。

### 1-4. ローカル LLM 対応 = 部分的なデータ主権

Ollama 対応（API キー不要・ローカル実行）は、MulmoClaude の「クラウド依存を排除し、
自分のマシンで動かす」思想と重なる。

### 1-5. エージェント群の状態可視化（MulmoTerminal 的役割）

MulmoTerminal が「どのエージェントが入力待ちか」を色分けで示すのと同じ問題意識を、
`VoiceSphere.vue` がすでに実装している。props ではなく `useChat` の `aiState` /
`pendingBodies` と `useSettings` の `bodies` を直接購読し、有効な体の数だけ粒子クラスタ
（最大3）に分裂させて、プロバイダー色（`constants/bodyProviders.ts`）で塗り分ける。
「複数エージェントの監督」という UI 役割を、ターミナルではなく球体という形で解いている。

### 1-6. API キーのクライアントサイド暗号化

`src/lib/keyVault.ts` の `encryptText` / `decryptText` により、API キーは平文ではなく
暗号化して localStorage に保存される（`useSettings.ts:79`）。
「認証情報をサーバーに預けない」という点で、データ主権の思想を一部すでに実装できている。

## 3. 今後の方向性 ― 音声対話ファースト

### 3-0. 前提テーゼ

**次に来るのは音声対話型であり、ThreeBody はそのために作られた。**
この前提を置くと、プロダクトの評価軸は「回答の質」から「**会話として成立するか**」に変わる。
判断基準は次の 3 つ。

1. 話しかけてから**最初の音が返るまで**の体感時間
2. AI の発話に**割り込めるか**
3. 手を一度も使わずに**一往復が完結するか**

以下の 3 本柱（音声対話 / MCP / マルチモーダル）は、すべてこの軸に従属させる。

---

### 3-1. 柱A：音声対話の作り直し（最優先・土台）

#### 現状のフロー

```
useWakeWord（常時ASR）「アイリス」検知
  → useVoiceInput 録音開始（recording=true の間ウェイクワードは停止）
  → 2.5秒の無音（SILENCE_MS）で確定
  → confirming で「この内容でいいか」確認
  → sendMessage
  → ストリーミング完了（streaming === false）を待つ
  → useTTS.speak で全文読み上げ
```

#### 課題（重い順）

| # | 課題 | 現状の根拠 | 方向性 |
|---|---|---|---|
| 1 | **最初の音が出るまでが長い** | `ChatView.vue:135` の watch が `streaming === false` を待ってから `speak()` する。三体モードでは「副体の並列応答（最大512トークン）→ 主体の統合をフルストリーム完了」まで完全に無音 | 文（句点）単位で逐次 TTS に流す。統合回答の最初の一文が出た時点で喋り始める |
| 2 | **割り込めない（barge-in 不在）** | TTS 再生中はマイクを開いていない。`useTTS.cancel()` は存在するが発話検知と結びついていない | 再生中も低感度で ASR を回し、ユーザー発話を検知したら即 `cancel()`。人間の会話は割り込みで成立する |
| 3 | **確認ステップが手を要求する** | `confirming` / `confirmText` で確認を挟む（`useVoiceInput.ts:49`） | 誤認識対策としては正しいが、ハンズフリーの理念と矛盾する。音声だけで訂正（「ちがう」「取り消して」）できるようにするか、確信度が高い場合はスキップする |
| 4 | **Web Speech API 依存** | `useVoiceInput.ts` / `useWakeWord.ts` とも `window.SpeechRecognition` 直叩き | Firefox 非対応。かつ Chrome では音声が Google のサーバーへ送られるため、**ローカル完結でなくデータ主権とも矛盾する**。ASR を差し替え可能な抽象レイヤに切り出し、Whisper 系（ローカル / API）へ移れるようにしておく |
| 5 | **ウェイクワードがフル ASR の文字列マッチ** | `WAKE_PATTERNS`（`アイリス`/`iris`/`あいりす`/`アイリ`）に対し常時 SpeechRecognition を回して `includes` 判定 | CPU・バッテリ・誤検知のコストが高い。専用の軽量ウェイクワード検知エンジンに置き換える |
| 6 | **TTS の声が OS 依存** | `useTTS.ts` の `pickVoice()` が Google/Microsoft/Apple の順で拾う | 「アイリス」というキャラクターの同一性が環境ごとに崩れる。音声対話が主役なら声はブランドそのもの。専用 TTS の検討価値がある |

#### 三体モードとの構造的な緊張（要方針決定）

三体モードは本質的に **2 ラウンド**（副体の並列応答 → 主体の統合）を要するため、
テキストでは「じっくり考えてくれている」と読めるが、**音声では単なる沈黙になる**。
音声ファーストと三体モードは、放置すると正面から衝突する。緩和の選択肢：

- **A. 主体先行**：主体が先に喋り始め、副体の見解は後から差分・補足として述べる
- **B. 音声時は縮退**：音声モードでは体数を減らす、または副体のトークン上限をさらに削る
- **C. 沈黙を埋める**：球体の分裂アニメーションと短い相槌（「三人で考えてる」等）で待ち時間を体験に変える

C は既存の `VoiceSphere.vue`（→ 1-5）とすぐ接続できるが、A が最も本質的。
実装前にどれを採るか決める必要がある。

---

### 3-2. 柱B：MCP の実接続

理念面で唯一の完全空白地帯（`grep -rni mcp` が 0 件）であると同時に、
**音声との相乗効果が最も大きい**機能でもある。

- 各「体」が検索・コード実行・外部 API を扱えるようになり、
  「3 つの視点で考える」→「3 つの視点で**調べて**考える」に価値が上がる
- 音声の文脈では価値がさらに増す。キーボードが使える状況より、
  **手がふさがっている状況（運転中・料理中・作業中）でこそツール実行の価値は跳ね上がる**
- ただし音声ではツール実行の待ち時間が沈黙として露骨に出る。
  柱A-1（逐次 TTS）と柱A の C 案（球体での状態表現）が先に要る

---

### 3-3. 柱C：マルチモーダル

音声ファーストにおける位置づけを明確にしておく。
MulmoChat が**視覚を主役**にするのに対し、ThreeBody は**音声が主・視覚が従**。
すなわち「声で聞いて、**必要なときだけ**画面に出す」。

- 出力側：`src/types/message.ts` の `ContentBlock` は `text` / `error` / `perspective` の 3 種のみ。
  ここに画像・図表などを追加し、`content_blocks` テーブル（`type` カラム）と合わせて拡張する
- 入力側（カメラ・画面共有）は、音声の往復が完成してからでよい

---

### 3-4. 進める順序と理由

```
柱A（音声の遅延と割り込み）  ← 体験の分水嶺。ここが直らないと他を足しても会話にならない
   ↓
柱B（MCP）                  ← 音声で「調べて」が通るようになり、価値が段違いに上がる
   ↓
柱C（マルチモーダル）        ← 音声で足りない部分を視覚が補う、という従属関係で設計できる
```

柱A を先にやる理由は単純で、**MCP もマルチモーダルも「待ち時間」を増やす方向の機能**だから。
沈黙を埋める仕組みが無いまま重い機能を足すと、体験は足すほど悪くなる。

> この 3 本柱は、4 章の一体型フェーズと合流して **1 本の実装計画（→ 4-2）** になる。
> 柱A / 柱B / 柱C はそれぞれ Phase 2 / Phase 5 / Phase 6 に対応する。
> **着手時に見るべきは 4-2 の一覧**で、この節はその根拠にあたる。

### 3-5. 上記と並行して効く小さな施策

本筋ではないが、コストが低く効果が明確なもの。

- **会話データのエクスポート** — JSON / Markdown で書き出せるだけでデータ主権のギャップが一段埋まる
- **コスト可視化** — 三体モードは 1 ターンで複数 API を叩く。概算コスト表示で安心して使い続けられる
- **体数の可変化** — `bodies` の 3 要素タプル固定（`useSettings.ts:25`）を配列に一般化。
  GraphAI 的な任意ノード数に近づくが、球体 UI とプロンプト設計の両方に波及するため後回しでよい

## 4. 一体型への移行 ― Apple I から Apple II へ

### 4-0. 問題の再定義：エンジニアと一般ユーザーの乖離

エンジニアにとって API キーは「持っているもの」だが、一般ユーザーにとっては
**存在すら知らないもの**であり、取得にはクレジットカード登録が要り、
従量課金という料金体系そのものが恐怖の対象になる。

彼らは「使いたい」だけであって、**部品を調達したいわけではない**。
アカウントを登録して動かないものは、その時点で離脱する。

この乖離は、現状のコードにそのまま現れている。

#### 決定的な事実：無料ユーザーは三体モードを一度も見られない

`backend/routes/chat.ts:81` の共有キー経路は `streamBodyOAI()` を 1 回呼ぶだけの**単体モード**である。

```
自分のキーを持つユーザー  → 三体モード（副体の並列 → 主体の統合）＝ ThreeBody の本体
共有キーのユーザー        → Anthropic 1 体のストリーミング   ＝ ただのチャット
```

つまり **プロダクト名の由来である中核機能が、最も獲得したい層に対してだけ不可視**になっている。
しかもその入口（`can_use_shared_key`）は招待制で、行が無ければ `not_permitted` に倒れる（`sharedKey.ts:76`）。

現状の ThreeBody は **Apple I** である。基板としては優れているが、
「電源とキーボードとケースは自分で用意してくれ」と言っている。

---

### 4-1. Apple II が実際にやったこと

Apple II が一般に届いたのは、性能が上がったからではなく**同梱物を変えたから**である。

| Apple II の同梱物 | 意味 |
|---|---|
| ケース・電源・キーボード | 買ってきて電源を入れれば動く |
| BASIC in ROM | 何も設定せずに、すぐ「使える状態」から始まる |
| **拡張スロット 8 本** | それでも開放性は捨てなかった（Wozniak が譲らなかった部分） |

重要なのは 3 つ目である。
**一体型にするとは、閉じることではない。**
既定を「何もしなくても動く」に置き換え、開放性は**スロットとして残す**ということ。

ThreeBody に翻訳すると：

| Apple II | ThreeBody での対応物 | 現状 |
|---|---|---|
| 電源 | 推論コスト（運営が負担する既定の枠） | 招待制・単体モードのみ |
| キーボード | **音声**（→ 3-1） | 実装済み。むしろ ThreeBody の強み |
| BASIC in ROM | 既定の三体構成（考えなくても 3 体が組まれている） | **無し**（ユーザーが 3 体を自分で設定する） |
| 拡張スロット | BYOK と Ollama | 実装済み（これは温存する） |

この対応表が、そのまま「一体型への補助線」になる。

### 4-2. 実装フェーズ（統合版）

音声 3 本柱（→ 3-1〜3-3）と一体型を 1 本の順序に統合したもの。**これが唯一の実装計画**とする。

> 番号の対応：旧「Phase 2（定額課金）」は Phase 4 へ、旧「柱A / 柱B / 柱C」は
> それぞれ Phase 2 / Phase 5 / Phase 6 に対応する。

| # | フェーズ | 一言でいうと | 前提 |
|---|---|---|---|
| 0 | 三体を既定にする | ThreeBody を名乗る最低条件 | なし |
| 1 | 入口を開ける | 登録すれば動く状態 | Phase 0 |
| 2 | 沈黙を消す | 音声が会話として成立する | なし（並行可） |
| 3 | 初回体験を通す | 設定ゼロで声だけで一往復 | Phase 0・1・2 |
| 4 | 定額課金 | 届いてから収益化する | Phase 3 |
| 5 | MCP | 「調べて」が声で通る | Phase 2 |
| 6 | マルチモーダル | 声で足りない分を視覚が補う | Phase 5 |

#### Phase 0：三体を既定にする

**目的** — 共有キーのユーザーにも三体モードを見せる。現状は単体モードで、
中核機能が最も獲得したい層にだけ不可視になっている（→ 4-0）。

**やること**

- [ ] `backend/routes/chat.ts:70-90` の共有キー分岐を、`streamBodyOAI()` 1 回から
      三体オーケストレーション（副体の並列 → 主体の統合）に差し替える
- [ ] 共有キー用の既定 `bodies` 構成を定義する。主体は Anthropic、
      副体は安価なプロバイダー（DeepSeek / 各社の Fast モデル）に逃がす混成にする
- [ ] `SHARED_DAILY_LIMIT` を 5 → 2〜3 に引き下げる
- [ ] 1 ターンあたりの実コストを実測し、見積もりと突き合わせる

**コスト見積もり**（レベル 2 ＝ `maxTokens: 4096` / `secondaryMaxTokens: 768`）

- 出力：副体 768×2 ＋ 主体 4096 ＝ 単体比 **約 +37.5%**
- 入力：体数分（約 3 倍）に増えるが、Fast モデル級では**出力が支配的**
- → 素朴な「3 倍」ではなく **概ね 2 倍以下**に収まる見込み（**要実測**）

**設計上のポイント**

- 副体を安価なプロバイダーに逃がせるのは、プロバイダー中立性（→ 1-2）があるから。
  理念が**経済的に効く**のがここ
- 「単体 5 回」より「**三体 2 回**」のほうがプロダクトを伝える。回数は削ってよい
- コストの主レバーは `SHARED_THINKING_LEVEL = 2` の固定（レベル 5 とは単価が約 40 倍違うと
  `sharedKey.ts:13` に記載）。**このレバーは触らず、体数だけを増やす**のが安全

**完了条件** — 自分の API キーを持たないユーザーが、三体モードの応答を受け取れる。

#### Phase 1：入口を開ける（招待制の反転）

**目的** — 「登録すれば動く」を成立させる。
なお正確には招待制の*撤廃*ではなく、**既定を許可に反転し、代わりに全体上限を設ける**こと。
許可リスト方式からブロックリスト方式への転換にあたる。

**やること**

- [ ] `docs/schema.sql:38` の `can_use_shared_key` を `default false` → `default true` に変更
- [ ] **既存行のバックフィル** — `default` は既存行に効かないため `update` が別途必要
- [ ] **行が無い場合の扱いを決める** — `checkSharedAllowance` は `error || !data` で
      `not_permitted` に倒す（`sharedKey.ts:76`）。既定値が何であれ、行が無ければ弾かれる
- [ ] **全体の日次上限（キルスイッチ）を追加** — 現状のレバーはすべて 1 ユーザー単位で、
      運営側の総額を守るものが無い
- [ ] 下記の競合を検証し、必要なら修正する

**先に潰すべき競合（未検証・要確認）**

`sendMessage` 内の `persistMessage(userMsg)` は **await されない** fire-and-forget で
（`useChat.ts:347` 付近）、その直後に `/api/chat` へ `fetch` が飛ぶ。
`user_setting` の行を作るのは `persistMessage → ensureConversation → createConversation →
ensureUserProfile` という奥の経路である。

```
persistMessage(...)   upsert user_setting → insert conversations  （2往復・await されない）
fetch('/api/chat')    checkSharedAllowance で user_setting を読む （1往復）
```

→ **新規ユーザーの初回メッセージで、行がまだ無い状態で読まれうる**。
結果は `not_permitted`＝無料枠が黙って効かない。獲得したいペルソナに正面から当たる。
対策は「バックエンド側で行が無ければ作る」または「ログイン直後に `ensureUserProfile` を await する」。

**すでに揃っているもの**（追加実装は不要）

- Google アカウント必須（未ログインは `not_signed_in`）
- 1 日あたりの上限（`consume_shared_quota` RPC で原子的に消費）
- 思考レベルの固定（`SHARED_THINKING_LEVEL`）

**完了条件** — 招待を受けていないアカウントが、ログイン後そのまま三体モードを使える。
かつ、運営側が総額を 1 か所で止められる。

---

#### Phase 2：沈黙を消す（音声の遅延と割り込み）

**目的** — 音声を「会話」として成立させる。詳細な課題一覧は 3-1 を参照。

**やること**

- [ ] **逐次 TTS** — `ChatView.vue:135` の watch が `streaming === false` を待つのをやめ、
      句点単位で `speak()` に流す。統合回答の最初の一文で喋り始める
- [ ] **barge-in** — TTS 再生中も低感度で ASR を回し、ユーザー発話を検知したら `useTTS.cancel()`
- [ ] **確認ステップの見直し** — `confirming` / `confirmText` を音声だけで閉じられるようにする
- [ ] **三体モードとの緊張への方針決定**（→ 3-1）— A：主体先行 / B：音声時は縮退 /
      C：球体と相槌で埋める。**実装前に決める**
- [ ] （後続）ASR を差し替え可能な抽象レイヤに切り出す。Web Speech API は Firefox 非対応で、
      Chrome では音声が Google のサーバーへ送られるためデータ主権とも矛盾する

**完了条件** — 話しかけてから最初の音が返るまでが、会話として不自然でない長さに収まる。
かつ、AI の発話に割り込める。

---

#### Phase 3：初回体験を通す（音声 × 一体型）

**目的** — 一般ユーザーにとっての「電源を入れたら動く」を成立させる。
音声においてそれは**「話しかけたら答える」**と同義であり、一体型と音声は同じ目標の裏表になる。

```
サインイン → 画面に球体がひとつ → 「話しかけてみて」
  → 喋る → 球体が3つに分裂して考える → 声で答える
```

**やること**

- [ ] 初回ログイン直後の導線を、設定画面ではなく**球体と「話しかけて」の一言**にする
- [ ] `EmptyBrainState.vue` の出し分けを、キー未設定前提から**「まず声で試せる」前提**に書き換える
- [ ] 未ログインでも再生できる音声デモを置く（キー無しで核の体験を伝える）

**完了条件** — **キーボード入力ゼロ・設定ゼロ**で一往復が完結する。
これが「箱から出して電源を入れる」に相当する。

#### Phase 4：定額課金

**目的** — 一般ユーザーが嫌うのは金額ではなく**従量課金という不確実性**。だから定額にする。

| 層 | 内容 | 狙い |
|---|---|---|
| 無料 | 1 日 N 回・三体モード・レベル 2 固定 | 「登録したら動く」を成立させる |
| 有料（月額） | 回数上限とレベル上限を引き上げ | 予測可能な支出。ここが一体型の本体 |
| BYOK / Ollama | 無制限・無料 | **拡張スロット**。エンジニアは自分で払う |

BYOK を無料のまま残すことが Apple II の拡張スロットに当たる。
一般ユーザーからは見えず、エンジニアには開いている。

**完了条件** — 無料枠を使い切ったユーザーが、金額を予測できる形で継続できる。

### 4-3. 理念との整合性

一体型（運営がキーを持ち、クラウドで課金する）は、一見すると
MulmoClaude のデータ主権・ベンダーロックイン回避と矛盾するように見える。
しかし Apple II の構造を採れば矛盾しない。

- **既定は一体型** — 一般ユーザーは何も知らずに使える
- **スロットは開いたまま** — BYOK と Ollama を残す限り、「自分のキー・自分のマシンで動かす」
  選択肢は失われない
- **データは持ち出せる** — 会話エクスポート（→ 3-5）を足せば所有権も担保できる

中嶋さんの理念を捨てて一般化するのではなく、
**理念をスロットとして残したまま、既定値だけを一般ユーザー向けに置き換える**。
これが引くべき補助線である。

---

### 4-4. 順序の根拠

実装フェーズの一覧は 4-2 にまとめた。ここではなぜその順序なのかだけ記す。

```
Phase 0  三体を既定にする        ← ThreeBody を名乗る最低条件
Phase 1  入口を開ける            ← 既定の反転＋全体上限。低コスト
   ↓                              （Phase 2 は 0・1 と並行して進められる）
Phase 2  沈黙を消す              ← 初回体験の分水嶺
   ↓
Phase 3  初回体験を通す          ← ここで「一般ユーザーに届く」が成立
   ↓
Phase 4  定額課金                ← 届いてから収益化する
   ↓
Phase 5  MCP                     ← 「調べて」が声で通る
   ↓
Phase 6  マルチモーダル          ← 声で足りない部分を視覚が補う
```

- **Phase 0・1 が先頭なのは、最も安く最も効くから。** 既存のレバー（レベル固定・日次上限・
  原子的な消費記録）はすでに動いており、足りないのは「共有キー経路を三体にする」ことと
  「既定を許可に反転し、全体上限を足す」ことだけ
- **Phase 2 が Phase 3 より前なのは、沈黙が長いままだと初回体験が「壊れている」と受け取られるから**
- **Phase 5・6 が後ろなのは、MCP もマルチモーダルも「待ち時間を増やす方向」の機能だから。**
  沈黙を埋める仕組みが無いまま重い機能を足すと、体験は足すほど悪くなる
- **Phase 4（課金）が Phase 3 の後なのは、届いていないものは売れないから**

---

## 5. 結論

ThreeBody は、中嶋さんの理念のうち
**「並列統合というグラフ実行構造」「プロバイダー中立性」「エージェント群の状態可視化」**を
すでに実装できている。残るギャップは **「データ主権」と「プラグインによる汎用コントローラー化」**。

その上で、今後の主軸は **音声対話ファースト**に置く。
Mulmo シリーズが「LLM＝汎用 OS」を視覚・個人データ・開発ワークフローの 3 方向から攻めているのに対し、
ThreeBody は **音声というインターフェースの方向から同じ地点を目指す**、という位置取りになる。

そして音声対話にとっての最大の敵は、モデルの賢さではなく**沈黙**である。
三体モードという「本質的に 2 ラウンドかかる構造」を抱えたまま音声を主役に据える以上、
レイテンシと割り込みの設計こそが ThreeBody 固有の技術的中核テーマになる。

同時に、届ける相手の設計も要る。現状の ThreeBody は Apple I であり、
**無料ユーザーは三体モードを一度も見られない**（→ 4-0）。
既定を「登録すれば三体が動く」に置き換え、BYOK と Ollama を拡張スロットとして残す。
理念を捨てるのではなく、理念をスロットに移して既定値を入れ替える ―
それが Apple I から Apple II への移行に相当する。
