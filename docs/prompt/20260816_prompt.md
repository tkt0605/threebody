## 目的

`buildSystemPrompt()` が積む6層（BASE_PERSONA + LANGUAGE + VOICE_STYLE +
LEVEL_STYLE + PRESET_EXTRA + 追加指示）を4層に減らし、設定の組み合わせ爆発を潰す。

これは機能削減ではなく **I3（SettingsDialog を開かずに恒常意図が確定する）への前倒し投資**。
会話側へ移すべき項目が少ないほど I3 が近くなる。

### 真の問題は層の数ではなく「軸の所有権」

「口調」を4箇所が同時に指示している。

| 層 | 口調について言っていること |
|---|---|
| `BASE_PERSONA` | 相槌は「なるほど」「そうか」のように自然な日本語で返す |
| `VOICE_STYLE.terse` | 前置き・**相槌**・感情表現は省く |
| `VOICE_STYLE.warm` | まず一言で受け止める：「なるほど」 |
| `LEVEL_STYLE[1]` | 一言か二文に絞る |
| `PRESET_EXTRA.coding` | 説明は簡潔に |

`terse` を選ぶと「相槌を省け」と「相槌を返せ」が**同時にLLMへ届く**。
`useSystemPrompt.ts` の冒頭コメントは既に「口調の指示はVOICE_STYLEに完全委譲」と
宣言しており、**設計意図は正しく実装が追いついていないだけ**。

作業後は各層の担当軸を1つに固定する。

| 層 | 担当する軸 | 触ってはいけない軸 |
|---|---|---|
| `BASE_PERSONA` | 振る舞い・出力形式 | 口調 |
| `LANGUAGE_PROMPT` | 言語 | — |
| `VOICE_STYLE` | **口調（唯一の権威）** | 長さ |
| 追加指示 | ユーザー固有 | — |

## Task 2: プロンプト層の矛盾解消

> 5タスク中、**唯一「今ユーザーに実害が出ている」項目**。他タスクへの依存が無いため先に置く。

`BASE_PERSONA` から**相槌に関する記述だけ**を外し、`VOICE_STYLE` 側へ一本化する。

- `BASE_PERSONA` の【会話の形式】にある「相槌は『なるほど』『そうか』のように自然な日本語で返す。」を**削除**
- ただし同じ行の「『> なるほど』のような引用記号（>）を相槌や受け止めに使わない。」は**出力形式のルールであって口調ではない**ため、【出力形式】ブロックへ移して残す
- `VOICE_STYLE` の4スタイルすべてで、相槌の扱いを明示する
  - `formal` / `casual` / `warm` — 相槌を返す（各スタイルの語彙で）
  - `terse` — 相槌を省く（現状の記述のままでよい）

**完了判定**: Task 1 のスナップショットに差分が出て、`terse` の出力から相槌を促す指示が消えていること。

## Task 3: preset の縮小（**丸ごと削除ではない**）

> ⚠️ 前版の指示は「preset を丸ごと削除」だったが、調査の結果**独自情報を持つものがある**ことが判明したため変更した。

| preset | 判定 | 根拠 |
|---|---|---|
| `chat` | **削除する** | 「会話の流れを大切に」は `BASE_PERSONA` の【会話の進め方】と完全重複 |
| `coding` | **テンプレートへ移す** | 「コードは動作するものを優先」「エラーは根本原因から」は他のどこにも無い |
| `creative` | **テンプレートへ移す** | `BodyPersona.optimist` と重複しない。**主体（一体）は `personaPrompt` を受け取らない**ため（`textService.ts` の統合呼び出しは `systemPrompt` を渡す） |

### やること

1. `PRESET_EXTRA` と `buildSystemPrompt()` 内の該当分岐を**削除**（これでプロンプト層が1つ減る）
2. `SettingsDialog.vue` 側に `PRESET_TEMPLATES` を新設する。**プロンプト層ではなく、追加指示欄（`systemPrompt`）に文章を流し込むテンプレート**として実装する

```ts
// SettingsDialog.vue — 選ぶと追加指示欄に文章が入り、ユーザーがその場で編集できる。
// プロンプトの層は増えない（追加指示は元から1層ある）
const PRESET_TEMPLATES: Record<string, string> = {
  coding:   'コードは動作するものを優先。エラーは根本原因から説明する。',
  creative: '創作の相談には積極的にアイデアを広げる。制約より可能性を語る。',
}
```

3. `Preset` 型と `Settings.preset` を削除。保存済みの `preset` キーが残っていても壊れないこと（Task 0 #2 により自然に満たされるはずだが、実際に確認する）

**なぜテンプレートにするか**: 独自情報を捨てずに層を減らせる上、**ユーザーが中身を見て編集できる**ようになる。設定を会話側へ移していく I3 の方向と一致する。

## Task 4: language を ja / en の2言語に

### 縮小の根拠

`settings.language` は3箇所を駆動しているが、**読み上げだけ既に2言語しかない**。

| 消費先 | 対応言語数 |
|---|---|
| `useSystemPrompt.ts` の `LANGUAGE_PROMPT` | 7 |
| `useVoiceInput.ts` の `LANG_LOCALE` | 7 |
| `ChatView.vue` の `ttsLang`（`settings.language === 'ja' ? 'ja-JP' : 'en-US'`） | **2** |

つまり中国語を選ぶと「認識は中国語・本文は中国語・**読み上げだけ英語**」になる。
現状は「7言語対応」ではなく「**5言語は読み上げが壊れている**」が正確。

### やること

1. `Language` 型を `'ja' | 'en'` に縮小
2. `LANGUAGE_PROMPT` を ja / en のみに
3. **`useVoiceInput.ts` の `LANG_LOCALE` も同時に縮小する**（型を narrow すると型エラーか死にキーとして残るため。前版の指示から漏れていた項目）
4. `SettingsDialog.vue` の `LANGUAGES` 配列を2件に
5. **保存済み値のフォールバックを実装する（必須）** — `useSettings.ts` の読み込みは型アサーションで実行時検証が無いため、保存済みの `'zh'` 等がそのまま通る。ホワイトリスト判定で `'ja'` へ落とす

```ts
// 例。実装形は現物に合わせてよいが、「型アサーションだけに頼らない」こと
const LANGUAGES = ['ja', 'en'] as const
function toLanguage(v: unknown): Language {
  return (LANGUAGES as readonly string[]).includes(v as string) ? (v as Language) : 'ja'
}
```

6. **コミットメッセージに「i18n 着手時に戻す前提での削除」と理由を残す**

## Task 5: thinkingLevel を3段階に

### 決定事項（実装者が選ばないこと）

`LEVEL_CONFIG`（`backend/llm/modelConfig.ts`）の5段階には実体がある。

| Lv | maxTokens | 固有設定 |
|---|---|---|
| 1 | 2048 | — |
| 2 | 4096 | — |
| 3 | 8192 | — |
| 4 | 16000 | `thinkingBudget: 8000` |
| 5 | 32000 | `adaptiveThinking: true` |

**決定**:

- **`LEVEL_CONFIG` は一切変更しない**（5エントリのまま残す）。`/api/chat` は curl 等フロントを介さない生のリクエストでも叩けるため、フロントが送らなくなることは経路を消す理由にならない
- **UI だけを3段階に集約し、送る値を `1` / `3` / `5` にする**
  - 低 → `1`（fast, 2048）
  - 中 → `3`（balanced, 8192）
  - 高 → **`5`**（powerful, 32000, adaptive thinking）
- **なぜ高を Lv5 にするか**: Lv4 の `thinkingBudget` は deprecated な機構で、Lv5 の adaptive thinking がその後継にあたる。「最も深い」というラベルとも一致する
- **保存済みの `2` / `4` は範囲外にせず、そのまま backend へ送って問題ない**（`LEVEL_CONFIG` に残っているため）。UI 上の表示は最も近い段階（2→低、4→高）にマッピングする

### やること

1. `LEVEL_STYLE`（プロンプト側の文体指示）を**削除**。`VOICE_STYLE` と競合しており、Lv1「一言か二文に絞る」と Lv2「要点だけコンパクトに」の差は日本語で表現できない
2. `ThinkingLevel` 型は `1 | 2 | 3 | 4 | 5` の**まま残す**（保存済み値と backend の受け口に合わせる）
3. `SettingsDialog.vue` の段階UIを3択（低/中/高 → `1`/`3`/`5`）に。保存済みの `2` / `4` は表示上いずれかへ寄せる

## Task 6: `Settings.provider` にコメントを追加（削除ではない）

> ⚠️ 前版の指示は「`settings.provider` と backend の単体モード経路を両方削除」だったが、
> 調査の結果**単体モード経路は到達可能**と判明したため、削除を中止して縮小した。

### 中止の根拠

- `chat.ts` の三体分岐は `available.length === 0` のとき **return せずに下へ抜ける**。3体すべてがクラウドでキー未設定、かつ共有キーが使えない場合がこれに当たり、`provider` の既定値 `'ollama'` により `streamOllamaNative` が走る＝**Ollama フォールバックとして機能している**
- さらに `chat.ts` 冒頭のコメントが「`/api/chat` は curl 等フロントを介さない生のリクエストでも叩ける」と明記している。**フロントが使っていないことは、API の経路が不要な理由にならない**

### やること（これだけ）

`SettingsDialog.vue` の `save()` が `settings.provider` を書き戻していないため、
既定値 `'ollama'` から動かない。**この事実をコメントで残し、次に読む人の誤読を止める。**

- `useSettings.ts` の `Settings.provider` 宣言の直上に、以下の趣旨のコメントを追加する
  - `SettingsDialog` の `save()` が書き戻さないため、実質 `'ollama'` 固定であること
  - backend の単体モード経路は、この既定値による Ollama フォールバックとして到達すること
  - 変更UIを足すか、`bodies` へ一本化するかは未決であること

**backend は一切変更しない。**

## 保留（本パスでは実装しない）

**`LENGTH_HINT` の追加** — Task 5 で `LEVEL_STYLE` を削除すると、`thinkingLevel` の
プロンプトへの影響がゼロになり、`maxTokens`（上限であって目標ではない）だけが残る。

  4: '【長さ】じっくりと。必要なだけ展開してよい。',
  5: '【長さ】じっくりと。必要なだけ展開してよい。',
