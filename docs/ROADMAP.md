## 1. 到達点：LLM OS（確定・再検討しない）

中島聡さんの `LLM_OS.md` が示す **Application-centric → Intent-centric** の転換を、「一人の人間が毎日使う OS」として実装する。

```text
ユーザー → 意図を表明 → LLMが理解 → Capabilityを組み合わせる → 必要なUIを生成 → 結果
```

ThreeBody 固有のテーマは、その意図処理を**単一の知性ではなく複数の視点で行い、その過程が見えて聞こえる**こと。

| 層 | 役割 | 現状 |
|---|---|---|
| **Layer 1 — LLM** | 考える | 実装済み（`backend/llm/providers/`：Anthropic / OpenAI / DeepSeek / Ollama） |
| **Layer 2 — Runtime** | 理解・判断・組み合わせ・実行 | **Perspective と Synthesis のみ実装済み。Intent / Capability 以降が未着手** |
| **Layer 3 — Computer** | 世界を動かす | 未着手（**I4** の MCP が入口） |

**すでに持っている資産**（新規に作る必要が無い）— Perspective の定義 `constants/bodyPersonas.ts` / 注入 `useSystemPrompt.ts:102` → `BodyConfig.personaPrompt` / 並列処理 `llm/textService.ts` `orchestrateMultiBody()` / 統合 `synthesis_start` → `text` / 可視化 `VoiceSphere.vue` ＋ `useVoiceNarration`。

`BodyPersona` は provider と直交しているため、**モデルが入れ替わっても ThreeBody は残る**。「三体＝固定の3モデル」ではなく「3つの異なる知性の協調」という抽象化は、コードの事実として既に成立している。新しい視点の追加は union 型への1行追加で済む。

## 3. フェーズ体系 I0〜I6

境界は「機能が増えたか」ではなく **意図がどこまで到達できるようになったか** で引く。

```text
記録される → 閉じる → （資金） → 持続する → 外界へ届く → 組み合わさる → 経路が増える
   I0        I1        I2         I3          I4          I5           I6
```

intent は**寿命の異なる4層**に割れ、保存先は寿命で決まる（既存の3テーブルにそのまま乗る。新アーキテクチャは要らない）。

| 意図の層 | 寿命 | 保存先 | 状態 |
|---|---|---|---|
| 発話意図（まだ喋る／言い切った） | 数百ms | 保存しない | **実装済み** `lib/endpointing.ts` |
| 要求意図（何をしてほしいか） | 1ターン | `messages` | I0・I3 |
| 課題意図（今日これを終わらせたい） | 会話1本 | `conversations` | I3（原始形は `.title`） |
| 恒常意図（短く答えて／日本語で） | 生涯 | `user_setting` | I3（現在は手動設定のみ） |

| Phase | 一言 | 完了条件（反証可能な形） |
|---|---|---|
| **I0** 記録 | 意図をデータにする（推論ゼロ・追加コストゼロ） | 停止・バージイン・言い直し・再質問が会話に紐づいて残る |
| **I1** 完結 | 声だけで一往復 | マイク許可後、**画面に一度も触れず**に 発話→応答→次の発話 が回る |
| **I2** 資金 | 課金（ゲート） | 有料プランが1件成立し、全体枠を上げても財布が破綻しない |
| **I3** 持続 | 意図が会話を越える | 恒常意図が1つ以上、**設定画面を開かずに**確定する |
| **I4** 到達 | 外界に触れる最初の穴 | MCP 1本が動き、**声から起動できる** |
| **I5** 編成 | 形が3種類揃ったら括り出す | 3種類の呼び出しが同じ入口を通り、不可逆操作だけが確認を要求する |
| **I6** 拡張 | 経路を増やす | 音声・テキスト以外の入出力が1つ通る |

**順序の根拠** — ① I0 が先頭なのは追加コストゼロで、貯め始めるのが早いほど価値が出るから。② I1 が I2 より前なのは、沈黙と「まず設定しろ」が残ったまま課金導線を作っても払う理由が立たないから（**売れる状態にしてから売る**）。③ I2 が Layer 3 より前なのは、**課金は遅らせるほど難しくなり**（後から上限を入れるとサービス劣化に見える）、**Capability層は遅らせるほど簡単になる**（実装が増えるほど抽象化の精度が上がる）から。難易度が時間で逆向きに動くので順序が決まる。加えてツール接続は入力トークンを増やし、**無料枠をさらに削る**。④ I3 が I4 より前なのは、Capability に渡す意図が先に存在する必要があるから。

> **抽象層は設計するものではなく、具体が3つ並んだときに「同じだ」と気づいて括り出すもの。**

### W1 — I0（記録）＋ I1（完結）を1本の作業として（M〜L）

**束ねる理由**: 両者は同じ発火点を触る。特に **I1(a) は `confirming` ブロックを廃止する**ため、I0 を先に実装するとその記録処理は I1 で消え、逆順なら新しい発火点へ足しに戻る。**どちらの順でも同じ場所を2度書く。**

- **W1-1 記録の器（S）** — `src/types/intent.ts`（新規）に `TurnSignals { interrupted: boolean; rephrased: number; repeatOf?: string }`。`useChat.ts`（`sendMessage` / `persistMessage`）と `docs/schema.sql` を更新。**スキーマだけは先に1回で確定させる**（貯め直しを避ける）。やらないこと: LLM呼び出し・分類器・`IntentRouter`・4個目のフィールド
- **W1-2 確認ステップの廃止（M）** — `useVoiceInput.ts:182-214` の `confirming` / `confirmSend` / `redo` を撤去し、`stop()` から直接 `onFinish(text)`。UI側は `ChatView.vue:307-312` / `VoiceSphereDialog.vue:55-56`。誤認識の取り消しは barge-in（`useWakeWord.ts:74`）に担わせる。**送信が可逆だから確認を外せる**——この判断は I5 の Permission 原則の先取りで、ここで決めたら I5 まで一貫させる。**残る論点**: バージインは割り込み後の発話しか拾えないため、直前の送信を破棄する動作が別途要る
- **W1-3 初回導線の反転（S）** — `EmptyBrainState.vue` の4分岐すべての着地（`:63` の「設定を開く」）を「まず声で試す」へ。`limit_reached` と `global_limit_reached` の区別は意図的なもので**潰さない**

### W2 — サーバー側の入力検証（I2 の必須前提・S）

`backend/routes/chat.ts` に `messages` の件数・サイズ検証。現状の切り詰めは `useChat.ts:110` の `HISTORY_LIMIT = 10` でフロントのみ、サーバー側は `express.json()` の既定100KBが事実上唯一の壁で意図した防御ではない。**課金より前に置く理由**: 有料ユーザーができた後の上限追加は「サービス劣化」に見える。**完了判定**: 巨大 `messages` の `curl` が 400、回帰テストが `backend/tests/chatRoute.test.ts` にある。

### W3 — I2 資金（★分水嶺・L）

設計は既にある: 無料＝三体固定レベル2 / 有料＝上限引き上げ / **BYOK・Ollama＝無制限無料**。**完了判定**: 有料プランが1件成立。

> **この順序が成立しない条件** — 課金がゲートなのは「次の10人がシェアキーの無料ユーザー」である場合のみ。**当面の対象を自分＋BYOK/Ollama ユーザーに絞るなら $0.5/日 の壁は存在せず**、W3 を後ろに送って W4 → W5 へ直行してよい。動かす場合は理由を本書に明記すること。

### W4 — I3 持続（M〜L）

`useChat.ts` の `switchConversation` / `startNewConversation` にフックし、`TaskIntent { goal; unresolved; constraints[] }` を抽出。**絶対の制約: 抽出をクリティカルパスに置かない**（応答前に挟むと W1 で消した沈黙が戻る）。**会話を離れるときに1回だけ**。Ollama があればローカルで回し、無ければスキップして **intent 無しでも動く**設計にする。**完了判定**: `SettingsDialog` を開かずに恒常意図が1つ確定する（例: 「短く」の反復 → 一度だけ訊いて `useSettings` へ昇格）。

### W5 — I4 到達（MCP 1本・M）

`backend/` に**ベタ書き**。新しいディレクトリを切らない。やらないこと: `Capability` インターフェース、レジストリ、Planning / Permission / Verification。**完了判定**: MCP 1本が**声から**起動する。

> **MCP と Capability は並列ではなく縦の関係。** MCP はプロトコル（どう繋ぐか）、Capability は設計概念（何ができるか）。MCP がカバーするのは `Execution` の一部だけで、**Planning / Permission / Verification は提供しない**。繋いでも Layer 2 は埋まらない——穴が開くだけで中身は自分で書く。なお Capability は MCP より広く、ThreeBody には既に MCP と無関係な capability が動いている（読み上げ・並列思考・永続化）。

### W6 — I5 編成（L）

**着手条件**: 呼び出しの**形が3種類**揃うこと。接続本数ではない（MCPサーバー1本が Tool を4個公開することがある。逆に3本繋いでも全部同じ形なら抽象化にならない）。ここで **Permission 原則**を実装として確定させる — **可逆な操作は推測して実行し、不可逆な操作は必ず訊く**（`DeleteAccountDialog.vue` の二段確認が先取り）。意図推定に要求される精度は操作の可逆性で決まるため、**I0〜I3 の推定が完璧でなくても Layer 3 を安全に開けられる**。

### W7 — I6 拡張

`ContentBlock`（`text` / `error` / `perspective`）に画像等を追加。

## 8. 更新ルール

> **新しいアイデアや考えが出ても、新規の md ファイルを作らない。本書を編集する。**
> 統合前は `docs/` にロードマップ的な文書が7本・計2,010行まで増え、同じ事実が重複して
> 古い記述が残っていた（実態と2件ずれていた実績あり）。分けた瞬間にどれが正本か分からなくなる。

**新しい考えが出たときの手順**

1. **7章と矛盾しないか** — 矛盾するなら、まず**決定を覆すだけの理由**が要る。無ければ書かない
2. **どのフェーズの完了条件を動かすか** — どれも動かさないなら、それは**書かなくてよい考え**。会話で終わらせる
3. **書くなら章を選ぶ** — 3章＝順序・完了条件 / 4〜6章＝着手点・検証手順・差し込み条件 / 7章＝決定と「やらない」判断
4. 分量が増えて読めなくなったら、**新ファイルを作らずに古い記述を削る**

**その他**
