## 到達点：LLM OS（2026-08-15 決定・確定事項）

**ThreeBody の到達点は LLM OS である。これは決定であり、以降の検討対象ではない。**
フェーズ体系 I0〜I6 は「そこへ至るための順序」であって、別方向の開発計画ではない。

### 何を作るのか

中島聡さんの `LLM_OS.md` が示す **Application-centric → Intent-centric** の転換を、
「一人の人間が毎日使う OS」として実装する。

```text
ユーザー → 意図を表明 → LLMが理解 → Capabilityを組み合わせる → 必要なUIを生成 → 結果
```

ThreeBody 固有のテーマは、その意図処理を**単一の知性ではなく複数の視点で行い、
その過程が見えて聞こえる**こと。これは他のどのLLM OS構想にも無い。

### 3層モデル

| 層 | 役割 | 現状 |
|---|---|---|
| **Layer 1 — LLM** | 考える（Anthropic / OpenAI / DeepSeek / Ollama） | 実装済み（`backend/llm/providers/`） |
| **Layer 2 — ThreeBody Runtime** | 理解する・判断する・組み合わせる・実行する | **Perspective と Synthesis のみ実装済み。Capability 以降が未着手** |
| **Layer 3 — Computer** | 世界を動かす（Browser / Files / Terminal / Network） | 未着手（**I4** の MCP が入口） |

**LLM は「脳」、ThreeBody Runtime は「神経系」**という位置づけ。
LLM を kernel そのものに置き換えるのではなく、intent orchestrator として使う。

### すでに持っている資産（新規に作る必要が無いもの）

「Perspective Engine を追加する」という構想は、実体としては**もう動いている**。

| 構想上の名前 | 実装 |
|---|---|
| Perspective の定義 | `src/constants/bodyPersonas.ts`（`optimist` / `skeptic` / `realist`） |
| Perspective の注入 | `useSystemPrompt.ts:102` `buildBodyPersonaPrompt()` → `BodyConfig.personaPrompt`（`llm/types.ts:10`） |
| 並列な視点処理 | `llm/textService.ts` `orchestrateMultiBody()` / `streamSecondaryBody()` |
| Synthesis → Decision | 主体（一体）による統合回答（`synthesis_start` → `text`） |
| 過程の可視化 | `VoiceSphere.vue`（体の数だけ粒子クラスタに分裂）＋ `useVoiceNarration`（相槌・逐次TTS） |

`BodyPersona` は provider と直交しているため、**モデルが入れ替わっても ThreeBody は残る**。
「三体＝固定の3モデル」ではなく「3つの異なる知性・役割の協調」という抽象化は、
思想としてだけでなくコードの事実として既に成立している。
新しい視点（例：`visionary`）の追加は union 型への1行追加で済み、新レイヤーを要さない。

### 到達までの順序

Layer 2 の残り（Capability / Planning / Execution / Permission / Verification）を
**抽象層として先に設計しない**。理由は2つ。

1. **抽象化する対象がまだ1個も無い** — 現在の Capability は「LLMと喋る」だけで、外部ツール実行の口は0件。実装が1個の段階で括り出すと、その1個の形に合わせた棚ができるだけで、2個目で作り直しになる
2. **今の律速はアーキテクチャではなく資金** — 全体枠 50回/日 で デイリーアクティブ30〜50人が上限。抽象層を作っても31人目は使えないままで、広げる原資は課金からしか出ない

したがって順序は以下で固定する。これを**フェーズ体系 I0〜I6** として展開したものが
「【現行】開発フェーズ体系」節であり、そちらが実装上の正本になる。

| # | やること | 意味 | 対応 |
|---|---|---|---|
| **1** | **意図を記録する**（推論ゼロ・追加コストゼロ） | 貯まるのに時間がかかる側から始める | **I0** |
| **2** | **声だけで一往復を閉じる**（確認ステップ＋初回導線） | 意図表明のインターフェースが完成する | **I1** |
| **3** | **課金** | 資金の壁を越える。ここを越えないと以降を作る時間が買えない | **I2** |
| **4** | **意図を会話の外へ持続させる** | Capability に渡す意図が先に存在している状態を作る | **I3** |
| **5** | **MCP を1本だけ繋ぐ** | 外界に触れる最初の穴。**Registry は作らない、ベタ書きでよい** | **I4** |
| **6** | **繋ぎ方の「形」が3種類揃った時点で共通部分を括り出す** | それが自然に `Capability Registry` になる。数えるのは接続本数ではない | **I5** |

> **抽象層は設計するものではなく、具体が3つ並んだときに「同じだ」と気づいて括り出すもの。**

### 2026-08-12 追加分その2（Phase 2：沈黙を消す）

**方針決定：C（球体＋相槌で埋める）を採用。** A（主体先行）は `orchestrateMultiBody` の
2ラウンド構造そのものと「統合回答」という三体の意味論を作り替える必要があり、
B（音声時は縮退）は Phase 0（無料ユーザーにも三体を見せる）と正面から衝突する。
Cはバックエンド変更ゼロで、既に体の数だけ粒子クラスタに分裂する `VoiceSphere` と直結できる。
**ただしCは実レイテンシを縮めない緩和策**であり、Aは将来の選択肢として残す。

| 内容 | 状態 |
|---|---|
| 逐次TTS（#4） | 解消。`lib/splitSentences.ts` で完成した文だけを切り出し、`useVoiceNarration.ts` が文ごとに読み上げへ流す。統合回答の最初の一文で喋り始める |
| 副体ラウンド中の無音（方針C） | 解消。`begin()` から `FILLER_DELAY_MS`(700ms) 後に「三人で考えています」を入れる。本文が先に始まったら出さない。単体モードでは出さない |
| バージイン（#5） | 解消。`useWakeWord` に `barge-in` モードを追加し、音声ラウンド中はウェイクワード無しで割り込める。割り込み時は読み上げと生成の両方を止める |
| エンドポインティング（#7） | 解消。`SILENCE_MS = 2500` 固定をやめ、`lib/endpointing.ts` が直前の認識文字列から 900〜3000ms を選ぶ（言い切り＝短く／接続助詞・フィラー＝長く） |
| マイクの持ち主が複数箇所に分散 | 解消。`ChatView` の `syncListening()` 1箇所で「録音中／音声ラウンド中／待機中」を決める |

**逐次TTSの注意** — `useTTS` は `speak()`（毎回 `cancel()` してから1発話）をやめ、
`enqueue()`（積むだけ）に置き換えた。`cancel()` を残したままだと、2文目が1文目を潰す。

**バージインの制約** — 割り込みを検知した時点の一言は、認識器を開き直す間に落ちる。
実際に送られるのは「割り込んだ後に話した内容」になる。自分の読み上げ音声で
自分が止まらないよう、`echoCancellation` の明示（前項）が前提になっている。

**残る穴** — 中断した応答は永続化しない（`aborted` 時は `persistMessage` を通らない）。
画面上には残るが、リロードすると消えてユーザー発言だけが「もう一度送信」の状態で残る。
会話切替による中断が切り替え先へ書き込んでしまう事故を防ぐための仕様で、
ユーザー起因の停止だけ保存するには中断理由の区別が要る。

### 導出の考え方

新体系は**意図（intent）の一生**を軸に切る。Phase の境界は「機能が増えたか」ではなく、
**意図がどこまで到達できるようになったか**で引く。

```text
記録される → 閉じる → （資金） → 持続する → 外界へ届く → 組み合わさる → 経路が増える
   I0        I1        I2         I3          I4          I5           I6
```

intent は単層ではなく、**寿命の異なる4層**に割れる。保存先は寿命で決まる。

| 意図の層 | 寿命 | 例 | 保存先 | 状態 |
|---|---|---|---|---|
| **発話意図** | 数百ms | まだ喋る／言い切った／考え中 | 保存しない（揮発） | **実装済み** `lib/endpointing.ts` |
| **要求意図** | 1ターン | 何を知りたい／何をしてほしい | `messages` | I0・I3 |
| **課題意図** | 会話1本 | 今日これを終わらせたい | `conversations` | I3（原始形は `conversations.title`） |
| **恒常意図** | ユーザー生涯 | 短く答えて／日本語で | `user_setting` | I3（現在は手動設定のみ） |

既存の `conversations` → `messages` → `content_blocks` の3テーブルにそのまま乗る。**新アーキテクチャは要らない。**

## 各フェーズの要点

### I0 — 記録（意図をデータにする）

**LLM呼び出しゼロ・追加コストゼロ。** 推論ではなく**事実**だけを拾う。

```ts
// src/types/intent.ts — 意図的に3フィールドだけ。増やしたくなったら我慢する
export interface TurnSignals {
  interrupted: boolean    // 停止 or バージイン = 「今の答えは要らなかった」
  rephrased: number       // 言い直し回数 = 「うまく言えていない」
  repeatOf?: string       // 同主旨の過去メッセージid = 「前の答えが刺さらなかった」
}
```

- **やること** — 発火点は既にある（`StopButton.vue` / `useWakeWord.ts` の barge-in / `useVoiceInput.ts` の interim 破棄）。**イベントを拾って会話に紐づけるだけ**
- **やらないこと** — LLM呼び出し、分類器、`IntentRouter`、4個目のフィールド
- **なぜ最初か** — ルーターは行き先が3つ揃えば半日で書けるが、**記録は貯まるまでに時間がかかり、スキーマを間違えると貯め直しになる**。図書館の分類体系は後から作れるが、蔵書は先に集め始めないと増えない
- **I1 と衝突しない理由** — barge-in も言い直しも I1 で触る発火点と同じ。新しいセンサーを足すのではなく、既存イベントに記録を1行足すだけ
- **推論より事実が強い理由** — 停止・バージイン・再質問は**外れない**。表情推定のような代理変数と違い、ユーザーの評価そのものが行動として残っている

### I1 — 完結（声だけで一往復）

旧 Phase 2 の残り1件と旧 Phase 3 を統合した。**この2つは同じ完了条件（指を使わずに意図が結果まで届く）を共有しており、分ける意味が無い。**

- **(a) 確認ステップの音声化** — `useVoiceInput.ts:182-214` の `confirming` / `confirmSend` / `redo` を抜けるのに、今も画面のタップが要る（`ChatView.vue:307-312` / `VoiceSphereDialog.vue:55-56`）。ハンズフリーの理念がここで切れている
  - **選択肢A** — 確認状態でも認識器を開き「はい／送って」「ちがう／もう一回」を拾う（barge-in 機構を流用）
  - **選択肢B** — **確認ステップ自体を廃止**し、無音タイムアウトで自動送信、誤認識はバージインで取り消す
  - **Bを推す。** 送信は可逆な操作であり、I5 で確定させる原則「可逆なら推測し、不可逆なら訊く」に従えば、そもそも確認を挟む必要が無い
- **(b) 初回導線の反転** — `EmptyBrainState.vue` は4分岐すべての着地が「設定を開く」ボタン（`:63`）。「使う前にまず設定しろ」は Apple I の思想。**「まず声で試せて、必要になってから設定へ行く」**に反転する
- **やらないこと** — ASR差し替え、ウェイクワード専用エンジン（横断トラックへ）
- **完了の判定方法** — 新規アカウントでログインし、**マウスとキーボードに触らずに**1往復できるか

### I2 — 資金（ゲート）

**このフェーズは OS 思想を1ミリも進めない。** それでも飛ばせない理由は、
全体枠 50回/日 ÷ 個人枠 3回/日 = **17人/日でゼロ**、実質デイリーアクティブ30〜50人で枯れるから。
抽象層を作っても31人目は使えないままで、無料枠を広げる原資は課金からしか出ない。

- 無料＝三体固定レベル2／有料＝上限引き上げ／BYOK・Ollama＝無制限無料（拡張スロットとして温存）
- **着手前に必ず**「サーバー側の入力検証」（`messages` の件数・サイズ）を入れる。有料ユーザーができた後に上限を入れると、サービス劣化として受け取られる
- 実測コストは1ターン ≈ $0.00998（Haiku 4.5、入力5,624＋出力871トークン）。単体比 約3倍。入力が3体分そのまま3倍化する影響が支配的

### I3 — 持続（意図が会話を越える）

**LLM OS の思想を、抽象層なしで最初に実証するフェーズ。**

- **抽出はクリティカルパスに置かない** — 応答前に分類用のLLM呼び出しを挟めば、I1 で消した沈黙が戻る。**ターン完了後**、しかも**毎ターンではなく会話を離れるとき**（`switchConversation` / `startNewConversation`）に1回だけ

```ts
export interface TaskIntent {
  goal: string          // 「〜したい」を1文で
  unresolved: boolean   // まだ達成されていないか
  constraints: string[] // 会話中に出た制約（「短く」「コードだけ」など）
}
```

- **コスト対策** — 会話あたり1回なので枠を圧迫しない。さらに **Ollama があればローカルで回す**（限界コストゼロ・データ主権と整合）。無ければスキップし、**intent 無しでも動く**設計にする
- **恒常意図への昇格** — `constraints` に「短く」が反復して現れたら、**一度だけ**訊いて `useSettings` へ昇格させる
- **なぜこれが思想の実証なのか** — `SettingsDialog.vue` の項目を1つずつ会話側へ移す作業だから。**「アプリを操作する → 意図を表明する」を、新レイヤーを建てずに検証できる**
- **やらないこと** — 毎ターン抽出、同期抽出、意図スキーマのフィールド4個以上

### I4 — 到達（外界に触れる最初の穴）

成果物は「Capability Registry」ではなく、**動く MCP 接続1本**。

- **やること** — MCPサーバーを1本だけ選び、`backend/` に**ベタ書き**で繋ぐ。抽象化しない
- **やらないこと** — `Capability` インターフェース、レジストリ、Planning／Permission／Verification の各層。**この時点では設計しない**
- **判断基準** — 「将来こうなるはずだから」で層を足さない。2本目・3本目が実際に現れてから足す
- **完了条件に「声から起動できる」を含める理由** — 繋いだだけでは Layer 3 に届いたことにならない。意図表明から実行までが1本で通って初めて到達したと言える

#### MCP と Capability の関係（2026-08-15 追記）

本書では両者を並べて書いている箇所があるが、**この2つは並列ではなく縦の関係**にある。
混同すると I4 の完了条件と、I5 で Registry を括り出すタイミングの両方を読み違える。

| | MCP | Capability |
|---|---|---|
| 種類 | プロトコル（規格） | 設計概念 |
| 答える問い | **どうやって繋ぐか** | **何ができるか** |
| 実体 | JSON-RPC 2.0 のメッセージ（stdio / Streamable HTTP） | 仕様としては存在しない。実装があるだけ |
| 差し替え | 別の規格（独自HTTP・関数直呼び）に置換可能 | 置換できない。無くせば機能が消える |
| 本リポジトリの現状 | **0件**（`grep -i mcp` はコードに1件もヒットしない。docs のみ） | 数件（`useTTS` の読み上げ、`orchestrateMultiBody` の並列思考、会話永続化） |

**Capability は MCP より広い。** ThreeBody には既に MCP と無関係な capability が動いており、
それが「外部の世界を動かす」種類でないだけである。したがって I4 の意味は
「Capability という概念を獲得する」ではなく、**外部の世界に触れる最初の穴を開ける**ことになる。

**MCP がカバーするのは `Execution` の一部だけ。**

| Layer 2 の層 | MCP が提供するか |
|---|---|
| Execution（呼び出しの実行） | **する** — これが MCP の本体 |
| Capability（何ができるかの記述） | 部分的 — Tool 名と JSON Schema は取れるが、ユーザーの意図との対応づけは取れない |
| Planning（複数を組み合わせる順序） | **しない** |
| Permission（やってよいかの判断） | **しない**（認可はアプリ側の責務） |
| Verification（結果が正しいかの確認） | **しない** |

MCP を繋いでも Layer 2 は埋まらない。**穴が開くだけで、中身は自分で書く。**
その「中身」を書くのが I5 であり、I3 で貯めた意図がその入力になる。

### I5 — 編成（形が3種類揃ったら括り出す）

#### 括り出す条件の正確な定義

従来「MCP接続が3本並んだら」と書いていたが、**接続の本数は本質ではない**。

- MCPサーバー1本は Tool を複数公開する（ファイル系なら「読む／書く／一覧／検索」で4個）。
  したがって **接続1本 ≠ capability 1個**であり、1本目の時点で繰り返しが目に見えることがある
- 逆に3本繋いでも全部が同じ形（全部 stdio・全部読み取り専用）なら、括り出しても抽象化にならない

**数えるべきは接続数ではなく、形の種類の数**（呼び出し方・権限確認の要否・結果の整形）。
種類が3つ揃って共通部分が目で見えた時点で抽出し、それを `Capability Registry` と呼ぶ。

#### Permission の設計原則（ここで確定させる）

**可逆な操作は推測して実行し、不可逆な操作は必ず訊く。**

- **可逆**（喋る・調べる・答える）→ 訊かない。外れたら barge-in が取り消し線として働く
- **不可逆**（削除・送信・課金・退会）→ 必ず確認。`DeleteAccountDialog.vue` の「削除」と打たせる二段確認が、既にこの原則の先取りになっている

**意図推定に要求される精度は、操作の可逆性で決まる。** 全部を高精度にする必要は無い。
この原則があるおかげで、I0〜I3 の意図推定が完璧でなくても Layer 3 を安全に開けられる。

### I6 — 拡張（経路を増やす）

Layer 3 の入出力チャネル拡張。`ContentBlock`（`text` / `error` / `perspective`）に画像等を追加する。

**カメラによる表情・感情推定は、ここに含めない（2026-08-15 判断）。** 理由は3つ。

1. 表情と感情の間に文化を越えて安定した対応関係が無い（Barrett et al. 2019, *Psychological Science in the Public Interest*）。**精度の問題ではなく、測定対象が存在しない**
2. 誤りのコストが非対称。当たって「普通」、外すと「監視されている」。期待値がマイナスに寄る
3. 顔特徴量は個人情報保護法の個人識別符号にあたり、EU AI Act では感情推認が職場・教育機関で禁止。既に自認しているデータ主権上の矛盾（Web Speech API が音声を Google へ送る件）を桁違いに広げる

過去に一度導入して削除した経緯がある（`60e692f` 導入 → `a5ea18b` `64b7593` `85d4d70` 削除、約12MB）。
**カメラを使うなら「感情」ではなく「在席・注視」に限定する**（2値・客観的・誤りのコストが小さい）。
在席検知なら「離席したら喋るのをやめる」「こちらを見ているならウェイクワード無しで聞く」という
用途が明確で、I1 のハンズフリー理念とまっすぐ繋がる。

- **運用上の注意** — `can_use_shared_key = false` の意味は「まだ招待していない」ではなく「運営が明示的に停止した」。停止アカウントは `[sharedKey] 停止中のアカウント（can_use_shared_key=false） user=...` としてログに出る。`docs/schema.sql` 6章ブロックBのバックフィル `UPDATE` は**二度と流さないこと**（停止アカウントが復活する）

## 順序の根拠

**I0 が先頭** — 追加コストゼロで、貯め始めるのが早いほど価値が出る唯一の項目だから。
かつ I1 で触る発火点と重なるため、I1 のついでに入る。

**I1 が I2 より前** — 沈黙と「まず設定しろ」が残ったまま課金導線を作っても、払う理由が立たない。
**売れる状態にしてから売る。**

**I2（資金）が Layer 3 より前** — 現在の律速はアーキテクチャではなく資金。
デイリーアクティブ30〜50人で全体枠が枯れる以上、**ここを越えないと I3 以降を作る時間そのものが買えない**。
思想上の優先度が低いからではなく、時間を買う唯一の手段だから前に置く。

**I3 が I4 より前** — Capability に意図を渡すには、渡す意図が先に存在する必要がある。
逆順にすると「行き先が1つしかないルーター」を作ることになる。

**I5 が最後の設計フェーズ** — Capability 層は**唯一「先に作ると必ず作り直しになる層」**。
Layer 2 の Perspective / Synthesis は既に動き、Presentation は I1 で閉じ、Intent は I0・I3 で埋まる。
残る Capability だけが具体ゼロなので、抽象から入ると実装1個分の形に固まる。

> **抽象層は設計するものではなく、具体が3つ並んだときに「同じだ」と気づいて括り出すもの。**

**したがって最短路は「LLM OS を作り始める」ではなく「LLM OS を作れる体力を先に作る」。**
順序は **I0 → I1 → I2 → I3 → I4 → I5 → I6** で固定する。
