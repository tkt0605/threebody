# ドメインドキュメント

コードベースを探索する際、エンジニアリング系スキルがこのリポジトリのドメインドキュメントをどう読むべきか。

## 探索前に読むもの

このリポジトリはスキルの既定レイアウトから外れている。ルート直下の`CONTEXT.md`や`docs/adr/`ではなく、**1ファイル**`docs/CONTENT.md`がある。以下の3つのH1セクションを持つ:

- `# 設計判断（旧ROADMAP）` — プロダクト／アーキテクチャ判断の唯一の正本（旧`docs/ROADMAP.md`、2026-09-01に削除）。中の章番号（`0章`、`①②③`、`2章`など）は固定されており、リポジトリ内のコードコメントから直接参照されている——**番号を振り直さないこと**。
- `# 用語集` — 用語集（本来`CONTEXT.md`が持つ内容）。用語を追加する際は`CONTEXT-FORMAT.md`のルールに従う。
- `# 負債棚卸し` — 技術負債・理解負債（存在はするが、なぜそうなっているかを誰も説明できない負債）の継続的な棚卸しリスト。上流スキルの標準的な構成には無い、このリポジトリ固有のもの。

探索前に該当セクションを読むこと。このリポジトリに`docs/adr/`は存在しない——作らないこと。ADR相当の判断は代わりに`設計判断（旧ROADMAP）`セクションに書く。`ADR-FORMAT.md`の3条件テスト（覆しにくいか／背景が無いと意外か／本物のトレードオフの結果か）の精神には従うが、判断ごとに別ファイルは作らない。

`docs/CONTENT.md`が万一存在しない場合は、黙って進めること。汎用の`CONTEXT.md`をデフォルトとして再作成しない——3セクション構成を復元する前に確認を取ること。

## 用語集の語彙を使う

出力（Issueタイトル、リファクタ提案、仮説、テスト名など）でドメイン概念に言及するときは、`docs/CONTENT.md`の`# 用語集`セクションで定義されている用語を使う。用語集が明示的に避けている同義語へ流れないこと。

必要な概念がまだ用語集に無い場合、それはシグナルである——プロジェクトが使っていない語を勝手に作っている（考え直す）か、本当のギャップがある（`/domain-modeling`向けに書き留める）かのどちらか。

## 矛盾を報告する

出力が`# 設計判断（旧ROADMAP）`内の判断と矛盾する場合は、黙って上書きせず明示的に報告する——特に「0. 絶対に動かさない前提」節は再検討しないと明言されているため、なおさら注意すること。
