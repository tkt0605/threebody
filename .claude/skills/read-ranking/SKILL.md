## 1. 状況を集める

以下を Bash で実行する。結果は判断材料であり、そのまま貼らない。

- `git status --short` — 変更されたファイルの一覧
- `git diff --stat` と `git diff` — 未ステージの差分
- `git diff --cached` — ステージ済みの差分（あれば）
- `ls -lt` を変更のあったディレクトリに対して実行 — 更新時刻の新しい順

**編集の順序について**: git は「どのファイルから編集を始めたか」を記録していない。
更新時刻は近似でしかなく、一括保存やフォーマッタが走ると壊れる。
順序が判別できないときは、判別できないと書く。推測で順序を作らない。

変更が0件、または前回の実行から差分が増えていなければ「変化なし」とだけ出力して終わる。

## 2. グループに束ねる。
変更されたファイルを「**一つの意図を実現するために連動して構築した塊**」ごとに束ねる。
ディレクトリやレイヤーで機械的に分けない。もし、backendディレクトリ と srcディレクトリ のファイルが同じ意図のためなら同じグループに入る。

- グループ数、グループ内のファイル数は無制限。
- 名前は動詞で書いた意図にする。Group1だけにしない。（例:「AをBにする。」）
- 同じグループに入れた根拠を1行書く（同じ型・同じイベント名・同じテーブルを触っている等、差分から確認できる事実に限る）
- フォーマット修正やtypoは「付随」グループに1つだけまとめる
- **意図が1つしか無いなら、グループは1つでよい。数を揃えるために割らない**
- どのグループにも入らないファイルが残ったら、無理に入れず末尾に列挙する

## 3. グループを並べる

グループ間の順序は**依存の向き**で決める。他のグループが前提にしている方が先。
依存が循環している、または独立していて順序が付かない場合は、その旨を書いて
横並びにする（無理に順位を付けない）。

グループ内のファイルの順序は、役割で決める。
契約（型・スキーマ・イベント定義）→ 中核 → 呼び出し側 → テスト。

## 4. 出力する

以下の形式だけを出力する。

---
**目的**: この変更が何を達成しようとしたか。1〜2行。

### 1. <意図を動詞で書いた名前>
なぜ先に読むか: 15字程度
まとまりの根拠: 差分から確認できる事実で1行
- `パス:行番号` — このファイルの役割（15字程度）
- `パス:行番号` — 〃

### 2. <同上>
...
---
